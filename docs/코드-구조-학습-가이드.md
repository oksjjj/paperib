# paperib 코드 구조 학습 가이드

이 문서는 이 저장소를 처음부터 다시 공부할 때 사용할 수 있도록 만든 코드 읽기 가이드다.

목표는 단순히 "어느 파일에 무엇이 있다"를 나열하는 것이 아니라, 실제 연구 파이프라인이 어떤 순서로 동작하는지 이해하는 것이다.

이 문서의 중심은 **모델 학습 코드**다.

처음부터 `labeling/tool.py`나 `labeling/app.py` 전체를 읽을 필요는 없다.
두 파일은 UI, plotting, label 관리, prediction 표시 기능까지 함께 들어 있어 모델 학습을 공부할 때는 범위가 너무 넓다.

따라서 다음 우선순위로 공부한다.

1. ContextAE / HourAE에 어떤 데이터가 들어오는가
2. train / valid / test가 어디서 나뉘는가
3. 정규화와 decontamination이 어떻게 수행되는가
4. HourAE가 어떻게 학습되는가
5. ContextAE가 HourAE와 무엇이 다른가
6. anomaly score가 어떻게 만들어지는가
7. VUS-PR과 threshold 평가가 어떻게 이루어지는가
8. RoCA baseline이 어떤 흐름으로 학습되는가
9. 필요할 때만 `labeling/tool.py`의 공통 데이터/label helper를 참고한다
10. UI 자체를 공부하고 싶을 때 마지막으로 `labeling/app.py`를 본다

# 2. 가장 먼저 알아야 할 데이터 흐름

전체 연구 흐름을 한 줄로 쓰면 다음과 같다.

```text
raw CSV
  ↓
labeling/preprocess.py
  ↓
사업자별 DataFrame 로딩
  ↓
11개 core feature 선택
  ↓
시간순 60% / 20% / 20% split
  ↓
TRAIN만으로 모델 학습
  ↓
VALID score 생성
  ↓
전문가 VALID label과 비교
  ↓
VUS-PR / Event-F1 / FA/day 평가
  ↓
최종 방법 고정 후 TEST 평가
```

중요한 원칙은 다음과 같다.

- train에는 anomaly label을 사용하지 않는다.
- ContextAE의 context 개수 K와 시간 경계도 train만으로 결정한다.
- validation label은 학습용 label이 아니라 개발 및 평가용이다.
- test는 최종 방법을 고정한 뒤 사용한다.

# 3. 모델 입력 feature는 어디서 결정되는가

모델 학습 코드를 읽다 보면 ContextAE와 HourAE의 `feature_columns()`에서
`metric_columns(df)`를 호출하는 부분이 나온다.

이때 **그 함수의 정의가 필요할 때만** `labeling/tool.py`를 참고하면 된다.

```python
CORE_FEATURES = (
    "M971",
    "M185",
    "M855",
    "M965",
    "M162",
    "M843",
    "M430",
    "M874",
    "M037",
    "M419",
    "M618",
)
```

그리고 `metric_columns(df)`가 실제 모델과 UI가 사용할 feature를 이 순서대로 반환한다.

핵심 함수:

```python
def metric_columns(df):
    present = set(df.columns)
    return [c for c in CORE_FEATURES if c in present]
```

따라서 ContextAE와 HourAE에서 별도로 feature list를 하드코딩하지 않아도 `metric_columns(df)`를 호출하면 동일한 11개 feature를 사용하게 된다.

이 구조의 목적은 다음과 같다.

```text
전문가가 anomaly 판단에 사용하는 feature
=
모델이 학습하는 feature
```

즉 모델이 전문가가 보지 않는 다른 counter 변화에 의해 높은 anomaly score를 만드는 문제를 줄이기 위한 구조다.

이 장에서 `tool.py`에서 확인할 것은 사실상 다음 두 가지뿐이다.

```text
CORE_FEATURES
metric_columns()
```

그 외 label 저장, prediction overlay, Plotly 관련 함수는 모델 학습 이해와 직접 관계가 없으므로 나중으로 미룬다.

# 4. train / valid / test 분할

ContextAE와 HourAE에서는 각자 `split_indices()`를 사용한다.

기본값:

```text
train = 앞 60%
valid = 다음 20%
test  = 마지막 20%
```

무작위 split이 아니라 시간순 split이다.

왜 중요한가?

시계열에서 미래 데이터를 과거 train에 섞으면 leakage가 생길 수 있기 때문이다.

ContextAE의 `prepare_unlabeled_plmn()` 흐름:

```text
load_plmn(plmn)
  ↓
11개 core feature 선택
  ↓
NaN / inf → 0 처리
  ↓
UTC timestamp 읽기
  ↓
Asia/Seoul local time 변환
  ↓
각 시점을 5분 slot 0~287로 변환
  ↓
60/20/20 split
```

여기서는 label을 읽지 않는다.

이 점이 매우 중요하다.

label은 모델 학습과 score 계산이 끝난 다음 `run()` 후반부에서 처음 읽힌다.

## 4.1 raw CSV가 모델 입력이 되기 전까지

원본 데이터는 `data/ib_data/raw/` 아래의 CSV에서 읽는다.

모델 코드에서 호출하는 `load_plmn()`의 실제 구현이 궁금할 때는
`labeling/tool.py::load_plmn()`만 찾아보면 된다.

이 함수와 `labeling/preprocess.py`의 기본 흐름은 다음과 같다.

```text
여러 raw CSV
  ↓
PLMN별 row 선택
  ↓
여러 파일의 같은 PLMN 데이터를 하나로 합침
  ↓
time 기준 오름차순 정렬
  ↓
time을 UTC datetime으로 변환
  ↓
PLMN별 pickle cache 저장
```

여기서 중요한 점은 이 단계에서는 모델용 정규화를 하지 않는다는 것이다.

즉 cache에는 기본적으로 원래 counter 값이 유지된다.

UI에서 사용하는 SUCCESS rate / ACCEPT rate 같은 파생 rate는 `add_rate_columns()`에서 만들어질 수 있지만,
현재 논문 모델 입력은 `metric_columns()`가 반환하는 11개 core counter만 사용하므로 rate는 모델 입력에서 제외된다.

## 4.2 모델 공통 결측값 / 비유한 값 처리

ContextAE, HourAE, RoCA 모두 모델 입력 직전에 11개 feature를 NumPy 배열로 바꾼다.

그 다음 다음 코드를 적용한다.

```python
values = np.nan_to_num(
    values,
    nan=0.0,
    posinf=0.0,
    neginf=0.0,
)
```

따라서:

```text
NaN  → 0
+inf → 0
-inf → 0
```

으로 처리된다.

즉 현재 구현에는 interpolation, forward-fill, backward-fill은 없다.

이 부분은 논문에서 전처리를 설명할 때 반드시 정확하게 써야 한다.

## 4.3 가장 중요한 원칙: scaler는 TRAIN에만 fit

모든 모델에서 validation/test의 분포 정보를 scaler 학습에 사용하면 leakage가 된다.

따라서 기본 원칙은 다음과 같다.

```text
TRAIN:
    scaler.fit(...)
    scaler.transform(...)

VALID:
    TRAIN에서 이미 fit한 scaler.transform(...)

TEST:
    TRAIN에서 이미 fit한 scaler.transform(...)
```

다만 모델별로 어떤 scaler를 어디에 fit하는지는 서로 다르다.

---

## 4.4 ContextAE / HourAE의 모델 입력 정규화: RobustScaler

ContextAE와 HourAE는 AutoEncoder 입력 정규화에 `RobustScaler`를 사용한다.

설정:

```python
RobustScaler(
    with_centering=True,
    with_scaling=True,
    quantile_range=(25.0, 75.0),
)
```

feature (f)에 대해 개념적으로 다음과 같이 변환된다.

$
x_f'
=
\frac{
x_f-\operatorname{median}(x_f)
}{
Q_{0.75}(x_f)-Q_{0.25}(x_f)
}
$

즉:

```text
중심 = median
scale = IQR = Q75 - Q25
```

이다.

평균과 표준편차를 쓰는 StandardScaler보다 outlier의 영향을 덜 받기 때문에,
contaminated train을 다루는 현재 문제에 더 적합한 정규화 방식으로 사용하고 있다.

### 왜 사업자 전체에 scaler 하나를 쓰지 않는가

HourAE에서는 **hour별**, ContextAE에서는 **context별**로 별도의 RobustScaler를 학습한다.

예를 들어 ContextAE가 두 context를 찾았다면:

```text
Context 0 raw train
→ RobustScaler 0

Context 1 raw train
→ RobustScaler 1
```

처럼 서로 다른 scaler가 존재한다.

따라서 같은 raw 값이라도 어느 context에 속하느냐에 따라 정규화된 값이 달라질 수 있다.

이것은 각 시간 context마다 정상 feature 분포가 다를 수 있다는 가정을 반영한다.

---

## 4.5 decontamination에서 scaler를 왜 두 번 fit하는가

ContextAE와 HourAE에서는 scaler도 Stage-1과 Final 단계에서 서로 다르다.

흐름:

```text
해당 context/hour의 contaminated raw TRAIN
  ↓
Stage-1 RobustScaler.fit()
  ↓
Stage-1 scaler.transform()
  ↓
Stage-1 AE 학습
  ↓
reconstruction MSE 상위 5% 제거
  ↓
retained raw TRAIN만 다시 선택
  ↓
Final RobustScaler.fit()
  ↓
Final scaler.transform()
  ↓
Fresh Final AE 학습
```

즉 Final scaler는 Stage-1 scaler를 그대로 쓰지 않는다.

이유는 상위 5% 후보를 제거한 뒤에는 정상으로 추정되는 데이터의 중앙값과 IQR 자체가 달라질 수 있기 때문이다.

따라서 decontamination은 다음 두 요소를 모두 다시 학습한다.

```text
1. scaler
2. AutoEncoder
```

중요한 점은 Final RobustScaler를 fit할 때 **제거되지 않은 TRAIN raw point만 사용한다**는 것이다.

validation/test는 절대 scaler fit에 참여하지 않는다.

---

## 4.6 validation/test point는 어떻게 정규화되는가

ContextAE에서는 먼저 각 point의 local time으로 context id를 정한다.

그 다음 해당 context의 **Final RobustScaler**로 변환한다.

```text
validation point x_t
  ↓
5분 slot 확인
  ↓
slot → context id
  ↓
그 context의 Final RobustScaler.transform(x_t)
  ↓
그 context의 Final AE
  ↓
reconstruction MSE
```

HourAE도 동일한 구조지만 context id 대신 hour를 사용한다.

```text
validation point x_t
  ↓
local hour 확인
  ↓
그 hour의 Final RobustScaler.transform(x_t)
  ↓
그 hour의 Final AE
```

따라서 valid/test를 별도로 다시 fit하거나 정규화 통계를 계산하지 않는다.

---

## 4.7 ContextAE의 context 탐색용 scaling은 모델용 scaling과 별개다

ContextAE에는 RobustScaler가 한 종류만 있는 것이 아니다.

시간 context를 찾기 위한 scaling과 AutoEncoder 학습용 scaling은 완전히 별개다.

context discovery 흐름:

```text
전체 TRAIN raw point
  ↓
clustering_input_scaler = RobustScaler.fit(TRAIN)
  ↓
TRAIN 전체를 robust scaling
  ↓
각 5분 slot별 across-day median / MAD 계산
  ↓
288개의 slot profile 생성
  ↓
profile_scaler = RobustScaler.fit(288 slot profiles)
  ↓
profile_matrix_scaled
  ↓
DP segmentation + silhouette
```

현재 core feature가 11개이고 median+MAD를 사용하므로 한 slot profile은:

```text
median 11차원
+
MAD 11차원
=
22차원
```

이다.

여기서 사용되는 두 scaler:

```text
clustering_input_scaler
profile_scaler
```

는 **시간 context를 찾기 위한 용도**다.

이 scaler들은 실제 AutoEncoder inference에 사용되는 Final RobustScaler와 다르다.

정리하면 ContextAE에는 크게 세 종류의 정규화 과정이 존재한다.

```text
A. context discovery용 TRAIN 전체 RobustScaler
B. 288 slot profile용 RobustScaler
C. 각 context AE용 Stage-1 / Final RobustScaler
```

세 역할을 혼동하지 않는 것이 중요하다.

---

## 4.8 Context profile에서 median과 MAD를 계산하는 위치

먼저 TRAIN raw feature를 `clustering_input_scaler`로 robust scaling한다.

그 다음 같은 5분 slot에 속한 여러 날짜의 값을 모은다.

예:

```text
Day 1 03:00
Day 2 03:00
Day 3 03:00
...
```

각 feature에 대해:

$
\operatorname{median}(x)
$

과

$
MAD
=
\operatorname{median}
\left(
|x-\operatorname{median}(x)|
\right)
$

를 계산한다.

따라서 MAD가 크다는 것은 해당 시간 slot에서 그 feature가 날짜마다 변동성이 크다는 뜻이다.

ContextAE는 단순히 "평균값이 비슷한 시간"만 묶는 것이 아니라,
기본 설정에서는 **중앙 수준과 변동성 패턴이 함께 비슷한 연속 시간대**를 찾는다.

---

## 4.9 ContextAE에서 관측되지 않은 5분 slot 처리

TRAIN에 특정 5분 slot이 아예 없는 경우도 방어적으로 처리한다.

이 경우 validation/test를 참고해서 채우지 않는다.

대신 TRAIN에서 관측된 slot 중 시계방향 거리상 가장 가까운 slot의 profile을 복사한다.

```text
누락 slot
→ TRAIN에서 가장 가까운 관측 slot 탐색
→ 그 profile 복사
```

23:55와 00:00도 가까운 것으로 계산하는 circular clock distance를 사용한다.

따라서 context discovery 과정에 validation/test 정보가 들어가지 않는다.

---

## 4.10 RoCA의 정규화: TRAIN-only MinMaxScaler

RoCA는 ContextAE/HourAE와 다른 정규화를 사용한다.

파일:

```text
common/data.py::prepare_plmn()
```

한 사업자의 11개 core feature 전체 TRAIN에 대해 `MinMaxScaler` 하나를 fit한다.

feature별로 개념적으로:

$
x_f'
=
\frac{x_f-x_{f,\min}^{train}}
{x_{f,\max}^{train}-x_{f,\min}^{train}}
$

이다.

흐름:

```text
전체 사업자 raw data
  ↓
시간순 60/20/20 split
  ↓
TRAIN 60%로 MinMaxScaler.fit()
  ↓
TRAIN transform
VALID transform
TEST transform
  ↓
window 생성
  ↓
RoCA 입력
```

중요한 점:

```text
VALID/TEST에 scaler.fit()을 다시 하지 않는다.
```

따라서 미래 데이터 정보가 train scaling에 들어가지 않는다.

또한 sklearn의 기본 MinMaxScaler는 transform 결과를 강제로 [0,1]에 clip하지 않는다.

따라서 validation/test 값이 TRAIN의 min/max 범위를 벗어나면:

```text
0보다 작은 값
또는
1보다 큰 값
```

이 나올 수도 있다.

이는 오류가 아니라 TRAIN 기준 범위를 벗어났다는 뜻이다.

## 4.11 모델별 전처리 비교

| 단계 | ContextAE | HourAE | RoCA |
|---|---|---|---|
| Feature | 11 core | 11 core | 11 core |
| NaN/±inf | 0으로 치환 | 0으로 치환 | 0으로 치환 |
| Split | 시간순 60/20/20 | 시간순 60/20/20 | 시간순 60/20/20 |
| 기본 scaler | RobustScaler | RobustScaler | MinMaxScaler |
| scaler 범위 | context별 | hour별 | 사업자 TRAIN 전체 |
| Stage-1 scaler | O | O | 해당 없음 |
| decontamination 후 scaler 재학습 | O | O | 해당 없음 |
| context 탐색용 추가 scaler | 2개 | 없음 | 없음 |

# 5. 왜 point-wise AutoEncoder인가

ContextAE와 HourAE의 기본 입력은 긴 window가 아니다.

한 시점의 입력 shape는 다음과 같다.

```text
x_t ∈ R^F
```

현재 F=11이다.

AutoEncoder 구조:

```text
11
 ↓
32
 ↓
8
 ↓
32
 ↓
11
```

코드:

```python
encoder:
    Linear(F, 32)
    ReLU
    Linear(32, 8)
    ReLU

decoder:
    Linear(8, 32)
    ReLU
    Linear(32, F)
```

학습 loss는 전체 feature에 대한 평균 reconstruction MSE다.

```text
MSE(x, x_hat)
```

최종 anomaly score도 point별 reconstruction MSE다.

$$
e_t = \frac{1}{F}\sum_{f=1}^{F}(x_{t,f}-\hat{x}_{t,f})^2
$$

point-wise라고 해서 시간 정보를 완전히 제거한 것은 아니다.

시간 정보는 "입력 window"가 아니라 "어떤 정상 모델을 사용할 것인가"를 결정하는 context에 들어간다.

즉 연구의 생각은 다음과 같다.

```text
긴 sequence 자체를 학습
          ↓
각 시점이 어느 시간대 정상분포에 속하는지 조건화
```

이를 수식으로 보면 다음과 같이 이해할 수 있다.

$$
p_N(x)
\quad\rightarrow\quad
p_N(x \mid c)
$$

# 7. decontamination의 정확한 동작

HourAE와 ContextAE 모두 같은 decontamination recipe를 사용한다.

ContextAE에서는 `fit_context_model()`,
HourAE에서는 `fit_hour()` 안에 들어 있다.

흐름:

```text
context/hour의 전체 contaminated train
  ↓
RobustScaler 학습
  ↓
Stage-1 AutoEncoder 학습
  ↓
각 train point의 reconstruction MSE 계산
  ↓
상위 5% reconstruction error 제거
  ↓
남은 raw train point만 추출
  ↓
RobustScaler를 다시 학습
  ↓
새 AutoEncoder를 처음부터 다시 학습
  ↓
Final normal model
```

기본값:

```python
stage1_remove_pct = 5.0
```

상위 5% cutoff는 다음 방식으로 계산된다.

```python
q = 1 - 5 / 100
cut = quantile(stage1_scores, q)
```

즉 95 percentile보다 reconstruction error가 큰 point를 제거한다.

중요한 점:

두 번째 모델은 첫 번째 모델을 이어서 fine-tuning하는 것이 아니다.

```text
Stage-1 AE
≠
Final AE의 초기 상태
```

남은 데이터로 새로운 AE를 다시 생성하여 학습한다.

또한 scaler도 다시 fit한다.

따라서 decontamination은 단순히 score 몇 개를 무시하는 것이 아니라, 최종 정상 분포 자체를 다시 구성하는 과정이다.

# 10. 시간대별 robust profile 생성

함수:

```python
build_train_slot_profiles()
```

이 함수는 TRAIN만 사용한다.

먼저 train 전체 feature를 RobustScaler로 변환한다.

그 다음 각 5분 slot에 대해 여러 날짜의 값을 모은다.

각 feature에 대해:

```text
median
MAD
```

를 계산한다.

기본 설정에서는 median과 MAD를 이어 붙인 vector가 한 slot의 profile이다.

11개 feature라면:

```text
median 11개 + MAD 11개
→ 22차원 slot profile
```

이렇게 하루 288개의 profile을 만든다.

왜 mean/std가 아니라 median/MAD인가?

train 자체가 contaminated 상태이기 때문에 anomaly의 영향을 상대적으로 덜 받는 robust statistic을 사용하기 위해서다.

# 11. 왜 일반 KMeans가 아닌 연속 구간 분할인가

이 제약은 `optimal_contiguous_partition()`에서 구현된다.

# 12. Dynamic Programming으로 시간 경계 찾기

두 함수가 핵심이다.

```python
build_segment_cost_matrix()
optimal_contiguous_partition()
```

`build_segment_cost_matrix()`는 모든 가능한 연속 시간구간에 대해 내부 SSE를 계산한다.

구간 [start, end)의 cost:

```text
해당 구간의 slot profile들이
구간 평균으로부터 얼마나 퍼져 있는가
```

그 다음 `optimal_contiguous_partition()`은 Dynamic Programming으로 정확히 K개의 연속 구간으로 나눌 때 전체 SSE가 최소가 되는 경계를 찾는다.

개념적으로:

$$
\min \sum_{k=1}^{K} SSE(C_k)
$$

subject to:

```text
각 C_k는 연속된 시간구간
각 구간은 최소 min_segment_slots 이상
```

이다.

1. DP로 가장 좋은 연속 구간 분할을 찾는다.

# 16. score calibration과 기본 3σ threshold

각 context의 최종 clean train reconstruction MSE에서:

```text
mean = μ_c
std  = σ_c
```

를 저장한다.

validation/test의 raw MSE를 다음과 같이 z 형태로 변환한다.

$$
z_t =
\frac{e_t - \mu_c}{\sigma_c}
$$

현재 기본 threshold:

$$
z_t > 3
$$

즉 코드의 `threshold_sigma=3.0`은 raw MSE 값 3을 의미하는 것이 아니라 context별 clean-train score 분포를 기준으로 한 z threshold다.

# 18. Event-F1과 Point-F1의 차이

Point metric:

각 5분 point를 개별 TP / FP / FN으로 계산한다.

# 21. POT / EVT 코드 읽는 법

POT는 높은 score tail만 따로 모델링한다.

먼저:

$$
u = Q_{0.98}(S)
$$

처럼 tail 시작점 u를 잡는다.

u보다 큰 score의 excess:

$$
Y = S-u
$$

에 Generalized Pareto Distribution을 fit한다.

코드:

```python
genpareto.fit(excess, floc=0)
```

그 다음 원하는 upper-tail probability α에 대응하는 threshold를 계산한다.

tail sample이 너무 적으면 empirical quantile로 fallback한다.

따라서 결과를 볼 때는 threshold 숫자만 보지 말고:

```text
n_exceedances
fallback 여부
GPD shape
GPD scale
```

도 함께 확인하는 것이 좋다.

# 23. RoCA 내부를 더 깊게 공부하기

RoCA는 단순 baseline 실행 코드만 보는 것으로는 이해하기 어렵다.

다음 연결을 반드시 따라가야 한다.

```text
RoCA/dataset.py
  ↓
RoCA/official/augmentations.py
  ↓
RoCA/official/network.py
  ↓
RoCA/official/loss.py
  ↓
RoCA/run_plmn.py
```

## 23.1 RoCA는 어떻게 contaminated train을 처리하는가

ContextAE는 Stage-1 reconstruction error 상위 5% point를 실제 train에서 제거한다.

반면 RoCA는 train sample을 삭제하지 않는다.

warmup 이후 각 batch에서 현재 anomaly score `loss_n`이 큰 상위 `nu` 비율을 잠재 anomaly로 간주한다.

기본:

```text
nu = 0.01
```

따라서 한 batch가 1000개라면 개념적으로:

```text
score가 낮은 약 990개 → normal candidate
score가 높은 약 10개 → anomaly candidate
```

로 나누는 방식이다.

실제 anomaly label은 사용하지 않는다.

## 23.2 RoCA anomaly score

`official/loss.py`의 `loss_n`이 핵심이다.

$
loss_n
=
(1-\cos(z,c))
+
(1-\cos(\hat z,c))
$

여기서:

```text
z      = 원본 window의 projected representation
z_hat  = decoder가 복원한 sequence의 projected representation
c      = hypersphere center
```

이다.

즉 representation이 center에서 멀수록 score가 커진다.

## 23.3 ContextAE와 RoCA contaminated 처리 차이

```text
RoCA
: sample을 제거하지 않고 loss 안에서 normal/anomaly candidate를 다르게 처리

ContextAE
: Stage-1 AE score 상위 5%를 train set에서 제거하고 fresh AE 재학습
```

따라서 두 모델의 비교는 단순 backbone 비교가 아니라 contaminated training 전략의 차이도 포함한다.

## 23.4 별도 상세 문서

RoCA만 집중해서 공부할 때는 다음 파일을 같이 본다.

```text
RoCA/PAPERIB.md
```

여기에는 window shape, augmentation, network, center, loss_n, warmup, nu,
dense scoring, train quantile threshold까지 코드 순서대로 자세히 정리되어 있다.

|---|---|
| 11개 core feature | `CORE_FEATURES`, `metric_columns()` |
| 사업자 raw DataFrame 로딩 | `load_plmn()` |
| 전문가 GT mask가 어떻게 만들어지는지 | `load_labels()`, `human_anomaly_mask()` |
| prediction score를 UI 데이터와 맞추는 방식 | `align_scores_to_df()` |
| 공통 VUS metric을 UI에서 다시 계산하는 부분 | `compute_vus_paper_metrics()` |

이 중에서도 **모델 학습 자체에 직접 필요한 것은 앞의 두 항목**이다.

다음 함수들은 당장 공부하지 않아도 된다.

```text
build_figure()
plot_series_window()
add_label_indicator()
add_model_indicator()
hover 관련 함수
zoom/pan 관련 함수
UI threshold mode 관련 함수
```

이들은 모델의 학습 원리를 이해한 뒤 UI를 공부할 때 보면 된다.

# 27. UI는 어떤 역할인가

UI의 주 목적은 모델 학습이 아니다.

다음 기능을 담당한다.

```text
1. 사업자 데이터 시각화
2. 전문가 anomaly label 작성/수정
3. 모델 anomaly score 표시
4. 모델 예측 segment 표시
5. valid/test metric 확인
6. threshold 방식 변경 후 결과 비교
```

핵심 파일은 다음 두 개지만, 둘 다 **후순위**다.

```text
labeling/tool.py
labeling/app.py
```

역할은 다음처럼만 기억하면 충분하다.

```text
tool.py
= 데이터/label/prediction/metric/plotting 공통 helper 모음

app.py
= Dash 화면 상태와 사용자 callback 제어
```

모델 학습을 이해하는 단계에서는 이 장을 건너뛰어도 된다.

# 34. 마지막으로 기억할 핵심

이 저장소의 연구 코드는 세 층으로 나눠 생각하면 가장 쉽다.

```text
[원본 데이터]
data/ib_data/raw/
        ↓
ContextAE/HourAE의 prepare_unlabeled_plmn()
        ↓
필요한 공통 helper만 labeling/tool.py에서 호출

        ↓

[모델]
RoCA/
HourAE/
ContextAE/

        ↓

[평가]
common/metrics.py
scripts/eval_vus.py
scripts/eval_contextae_thresholds.py

        ↓

[사람이 확인하는 화면 — 후순위]
labeling/tool.py의 plotting helper
labeling/app.py
```

현재 논문의 핵심 구현은 UI가 아니라 다음 두 부분이다.

```text
1. TRAIN-only adaptive temporal context discovery
2. context-wise iterative decontamination
```

따라서 교수님께 연구 방법을 설명하기 전에는 우선 ContextAE의 다음 연결을 완전히 이해하는 것이 가장 중요하다.

```text
5분 slot
→ median/MAD profile
→ 연속 시간구간 DP 분할
→ silhouette로 K 선택
→ context별 Stage-1 AE
→ 상위 5% 제거
→ Final AE 재학습
→ context별 anomaly score
→ VUS-PR 평가
```
