# paperib 코드 구조 학습 가이드

이 문서는 이 저장소를 처음부터 다시 공부할 때 사용할 수 있도록 만든 코드 읽기 가이드다.

목표는 단순히 "어느 파일에 무엇이 있다"를 나열하는 것이 아니라, 실제 연구 파이프라인이 어떤 순서로 동작하는지 이해하는 것이다.

우선순위는 다음과 같다.

1. 데이터가 어디서 들어오는가
2. 어떤 11개 feature를 사용하는가
3. train / valid / test가 어디서 나뉘는가
4. HourAE가 어떻게 학습되는가
5. ContextAE가 HourAE와 무엇이 다른가
6. decontamination이 정확히 어디서 수행되는가
7. anomaly score와 threshold가 어떻게 계산되는가
8. VUS-PR 등 평가지표가 어떻게 계산되는가
9. RoCA baseline은 어떤 흐름으로 동작하는가
10. 마지막으로 labeling UI가 데이터를 어떻게 불러오고 보여주는가

# 2. 가장 먼저 알아야 할 데이터 흐름

전체 연구 흐름을 한 줄로 쓰면 다음과 같다.

```text
raw CSV
  ↓
labeling/preprocess.py
  ↓
사업자별 DataFrame 로딩
  ↓
11개 core feature 선택
  ↓
시간순 60% / 20% / 20% split
  ↓
TRAIN만으로 모델 학습
  ↓
VALID score 생성
  ↓
전문가 VALID label과 비교
  ↓
VUS-PR / Event-F1 / FA/day 평가
  ↓
최종 방법 고정 후 TEST 평가
```

중요한 원칙은 다음과 같다.

- train에는 anomaly label을 사용하지 않는다.
- ContextAE의 context 개수 K와 시간 경계도 train만으로 결정한다.
- validation label은 학습용 label이 아니라 개발 및 평가용이다.
- test는 최종 방법을 고정한 뒤 사용한다.

# 3. 11개 core feature는 어디서 결정되는가

가장 먼저 볼 파일은 `labeling/tool.py`다.

```python
CORE_FEATURES = (
    "M971",
    "M185",
    "M855",
    "M965",
    "M162",
    "M843",
    "M430",
    "M874",
    "M037",
    "M419",
    "M618",
)
```

그리고 `metric_columns(df)`가 실제 모델과 UI가 사용할 feature를 이 순서대로 반환한다.

핵심 함수:

```python
def metric_columns(df):
    present = set(df.columns)
    return [c for c in CORE_FEATURES if c in present]
```

따라서 ContextAE와 HourAE에서 별도로 feature list를 하드코딩하지 않아도 `metric_columns(df)`를 호출하면 동일한 11개 feature를 사용하게 된다.

이 구조의 목적은 다음과 같다.

```text
전문가가 anomaly 판단에 사용하는 feature
=
모델이 학습하는 feature
```

즉 모델이 전문가가 보지 않는 다른 counter 변화에 의해 높은 anomaly score를 만드는 문제를 줄이기 위한 구조다.

# 4. train / valid / test 분할

ContextAE와 HourAE에서는 각자 `split_indices()`를 사용한다.

기본값:

```text
train = 앞 60%
valid = 다음 20%
test  = 마지막 20%
```

무작위 split이 아니라 시간순 split이다.

왜 중요한가?

시계열에서 미래 데이터를 과거 train에 섞으면 leakage가 생길 수 있기 때문이다.

ContextAE의 `prepare_unlabeled_plmn()` 흐름:

```text
load_plmn(plmn)
  ↓
11개 core feature 선택
  ↓
NaN / inf → 0 처리
  ↓
UTC timestamp 읽기
  ↓
Asia/Seoul local time 변환
  ↓
각 시점을 5분 slot 0~287로 변환
  ↓
60/20/20 split
```

여기서는 label을 읽지 않는다.

이 점이 매우 중요하다.

label은 모델 학습과 score 계산이 끝난 다음 `run()` 후반부에서 처음 읽힌다.

# 5. 왜 point-wise AutoEncoder인가

ContextAE와 HourAE의 기본 입력은 긴 window가 아니다.

한 시점의 입력 shape는 다음과 같다.

```text
x_t ∈ R^F
```

현재 F=11이다.

AutoEncoder 구조:

```text
11
 ↓
32
 ↓
8
 ↓
32
 ↓
11
```

코드:

```python
encoder:
    Linear(F, 32)
    ReLU
    Linear(32, 8)
    ReLU

decoder:
    Linear(8, 32)
    ReLU
    Linear(32, F)
```

학습 loss는 전체 feature에 대한 평균 reconstruction MSE다.

```text
MSE(x, x_hat)
```

최종 anomaly score도 point별 reconstruction MSE다.

$$
e_t = \frac{1}{F}\sum_{f=1}^{F}(x_{t,f}-\hat{x}_{t,f})^2
$$

point-wise라고 해서 시간 정보를 완전히 제거한 것은 아니다.

시간 정보는 "입력 window"가 아니라 "어떤 정상 모델을 사용할 것인가"를 결정하는 context에 들어간다.

즉 연구의 생각은 다음과 같다.

```text
긴 sequence 자체를 학습
          ↓
각 시점이 어느 시간대 정상분포에 속하는지 조건화
```

이를 수식으로 보면 다음과 같이 이해할 수 있다.

$$
p_N(x)
\quad\rightarrow\quad
p_N(x \mid c)
$$

# 7. decontamination의 정확한 동작

HourAE와 ContextAE 모두 같은 decontamination recipe를 사용한다.

ContextAE에서는 `fit_context_model()`,
HourAE에서는 `fit_hour()` 안에 들어 있다.

흐름:

```text
context/hour의 전체 contaminated train
  ↓
RobustScaler 학습
  ↓
Stage-1 AutoEncoder 학습
  ↓
각 train point의 reconstruction MSE 계산
  ↓
상위 5% reconstruction error 제거
  ↓
남은 raw train point만 추출
  ↓
RobustScaler를 다시 학습
  ↓
새 AutoEncoder를 처음부터 다시 학습
  ↓
Final normal model
```

기본값:

```python
stage1_remove_pct = 5.0
```

상위 5% cutoff는 다음 방식으로 계산된다.

```python
q = 1 - 5 / 100
cut = quantile(stage1_scores, q)
```

즉 95 percentile보다 reconstruction error가 큰 point를 제거한다.

중요한 점:

두 번째 모델은 첫 번째 모델을 이어서 fine-tuning하는 것이 아니다.

```text
Stage-1 AE
≠
Final AE의 초기 상태
```

남은 데이터로 새로운 AE를 다시 생성하여 학습한다.

또한 scaler도 다시 fit한다.

따라서 decontamination은 단순히 score 몇 개를 무시하는 것이 아니라, 최종 정상 분포 자체를 다시 구성하는 과정이다.

# 10. 시간대별 robust profile 생성

함수:

```python
build_train_slot_profiles()
```

이 함수는 TRAIN만 사용한다.

먼저 train 전체 feature를 RobustScaler로 변환한다.

그 다음 각 5분 slot에 대해 여러 날짜의 값을 모은다.

각 feature에 대해:

```text
median
MAD
```

를 계산한다.

기본 설정에서는 median과 MAD를 이어 붙인 vector가 한 slot의 profile이다.

11개 feature라면:

```text
median 11개 + MAD 11개
→ 22차원 slot profile
```

이렇게 하루 288개의 profile을 만든다.

왜 mean/std가 아니라 median/MAD인가?

train 자체가 contaminated 상태이기 때문에 anomaly의 영향을 상대적으로 덜 받는 robust statistic을 사용하기 위해서다.

# 11. 왜 일반 KMeans가 아닌 연속 구간 분할인가

ContextAE에서는 멀리 떨어진 시간을 같은 context로 섞지 않는다.

예를 들어 아래처럼 만드는 것을 허용하지 않는다.

```text
Context A = 02:00 + 14:00 + 22:00
```

각 context는 반드시 연속 시간이어야 한다.

```text
Context 0: 00:00 ~ 06:55
Context 1: 07:00 ~ 23:55
```

이 제약은 `optimal_contiguous_partition()`에서 구현된다.

# 12. Dynamic Programming으로 시간 경계 찾기

두 함수가 핵심이다.

```python
build_segment_cost_matrix()
optimal_contiguous_partition()
```

`build_segment_cost_matrix()`는 모든 가능한 연속 시간구간에 대해 내부 SSE를 계산한다.

구간 [start, end)의 cost:

```text
해당 구간의 slot profile들이
구간 평균으로부터 얼마나 퍼져 있는가
```

그 다음 `optimal_contiguous_partition()`은 Dynamic Programming으로 정확히 K개의 연속 구간으로 나눌 때 전체 SSE가 최소가 되는 경계를 찾는다.

개념적으로:

$$
\min \sum_{k=1}^{K} SSE(C_k)
$$

subject to:

```text
각 C_k는 연속된 시간구간
각 구간은 최소 min_segment_slots 이상
```

이다.

---

# 13. K는 어떻게 정하는가

기본 후보:

```text
K = 2 ... 24
```

각 K마다:

1. DP로 가장 좋은 연속 구간 분할을 찾는다.
2. 그 분할의 silhouette score를 계산한다.
3. 가장 silhouette가 높은 K를 선택한다.

함수:

```python
fit_context_segmentation()
```

중요:

K 선택에도 validation label은 사용하지 않는다.

전부 TRAIN profile만 사용한다.

따라서 ContextAE의 context discovery 자체는 비지도 방식이다.

# 15. ContextAE 전체 run() 흐름

`ContextAE/run_plmn.py::run()`을 읽을 때 다음 순서로 보면 된다.

```text
1. seed 설정
2. device 선택
3. unlabeled PLMN 데이터 준비
4. TRAIN 5분 slot profile 생성
5. TRAIN-only context segmentation
6. train / valid / test에 context id 부여
7. context별 Stage-1 AE
8. 상위 5% 제거
9. context별 Final AE 재학습
10. train / valid / test score 계산
11. checkpoint 저장
12. 여기까지 끝난 뒤 expert label 로드
13. validation 평가
14. prediction JSON 저장
15. 필요할 때만 test 평가
16. 기본 실행이면 HourAE도 같은 조건으로 실행
```

코드를 설명할 때 가장 중요한 문장은 다음이다.

> 모델 학습과 anomaly score 생성이 끝난 뒤에 전문가 label을 불러온다.

# 16. score calibration과 기본 3σ threshold

각 context의 최종 clean train reconstruction MSE에서:

```text
mean = μ_c
std  = σ_c
```

를 저장한다.

validation/test의 raw MSE를 다음과 같이 z 형태로 변환한다.

$$
z_t =
\frac{e_t - \mu_c}{\sigma_c}
$$

현재 기본 threshold:

$$
z_t > 3
$$

즉 코드의 `threshold_sigma=3.0`은 raw MSE 값 3을 의미하는 것이 아니라 context별 clean-train score 분포를 기준으로 한 z threshold다.

# 18. Event-F1과 Point-F1의 차이

Point metric:

각 5분 point를 개별 TP / FP / FN으로 계산한다.

Event metric:

연속 anomaly 구간을 하나의 event로 보고, 예측 event와 GT event가 겹치면 hit로 처리한다.

따라서 운영 관점에서는:

```text
이상 구간 일부라도 탐지
```

하는 것이 의미가 있을 수 있으므로 Event Recall도 같이 확인해야 한다.

---

# 19. False Alarms / day

`false_alarms_per_day()`는 GT anomaly와 전혀 겹치지 않는 예측 event를 false alarm event로 센다.

그 다음 관측 기간의 일수로 나눈다.

$$
FA/day =
\frac{\text{false alarm event 수}}
{\text{관측 일수}}
$$

실제 운영에서는 단순 Point-F1보다 중요한 지표가 될 수 있다.

# 21. POT / EVT 코드 읽는 법

POT는 높은 score tail만 따로 모델링한다.

먼저:

$$
u = Q_{0.98}(S)
$$

처럼 tail 시작점 u를 잡는다.

u보다 큰 score의 excess:

$$
Y = S-u
$$

에 Generalized Pareto Distribution을 fit한다.

코드:

```python
genpareto.fit(excess, floc=0)
```

그 다음 원하는 upper-tail probability α에 대응하는 threshold를 계산한다.

tail sample이 너무 적으면 empirical quantile로 fallback한다.

따라서 결과를 볼 때는 threshold 숫자만 보지 말고:

```text
n_exceedances
fallback 여부
GPD shape
GPD scale
```

도 함께 확인하는 것이 좋다.

# 22. RoCA baseline 구조

우리 연구에서 직접 읽어야 할 파일:

```text

```

`RoCA/official/`은 외부 공개 원본 구현이므로 우선 블랙박스에 가깝게 두고 wrapper 흐름을 먼저 이해하는 것이 좋다.

```text
prepare_plmn()
  ↓
window 생성
  ↓
RoCAWindowDataset
  ↓

  ↓

  ↓
train score quantile threshold
  ↓
validation 평가
```

ContextAE/HourAE와 가장 큰 차이는 RoCA가 window 기반이라는 점이다.

# 23. common/data.py를 읽을 때 주의할 점

`common/data.py::prepare_plmn()`은 RoCA 같은 window 기반 baseline에서 사용하기 편하도록 만들어져 있으며 label도 함께 준비한다.

반면 ContextAE / HourAE는 label leakage를 더 명확하게 차단하기 위해 각 파일 내부의:

을 사용한다.

따라서 두 함수를 같은 함수라고 생각하면 안 된다.

# 25. UI는 어떤 역할인가

UI의 주 목적은 모델 학습이 아니다.

다음 기능을 담당한다.

```text
1. 사업자 데이터 시각화
2. 전문가 anomaly label 작성/수정
3. 모델 anomaly score 표시
4. 모델 예측 segment 표시
5. valid/test metric 확인
6. threshold 방식 변경 후 결과 비교
```

핵심 파일:

```text
labeling/app.py
labeling/tool.py
```

처음 공부할 때 `app.py` 전체를 처음부터 끝까지 읽는 것은 비효율적이다.

먼저 `tool.py`를 읽고, 그 다음 `app.py`의 데이터 로딩 callback만 읽는 것이 좋다.

# 26. labeling/tool.py 역할

`tool.py`는 UI의 실질적인 backend utility에 가깝다.

중요한 영역:

```text
CORE_FEATURES / metric_columns()
load_plmn()
load_labels() / save_labels()
load_predictions()
human_anomaly_mask()
compute_detection_metrics()
compute_vus_paper_metrics()
ensure_score_column()
build_figure()
```

즉:

```text
app.py = 사용자 이벤트 / 화면 상태
tool.py = 데이터 / metric / plot 로직
```

으로 생각하면 이해하기 쉽다.

# 33. 마지막으로 기억할 핵심

이 저장소의 연구 코드는 세 층으로 나눠 생각하면 가장 쉽다.

```text
[데이터/정답]
labeling/tool.py
data/ib_data/

        ↓

[모델]
RoCA/

        ↓

```

현재 논문의 핵심 구현은 UI가 아니라 다음 두 부분이다.

```text
1. TRAIN-only adaptive temporal context discovery
2. context-wise iterative decontamination
```

따라서 교수님께 연구 방법을 설명하기 전에는 우선 ContextAE의 다음 연결을 완전히 이해하는 것이 가장 중요하다.

```text
5분 slot
→ median/MAD profile
→ 연속 시간구간 DP 분할
→ silhouette로 K 선택
→ context별 Stage-1 AE
→ 상위 5% 제거
→ Final AE 재학습
→ context별 anomaly score
→ VUS-PR 평가
```
