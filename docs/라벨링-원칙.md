# IB Inbound Roaming 라벨링 원칙 (초안)

연구용 inbound roaming 시계열에 **사람 라벨**을 붙일 때의 공통 원칙이다.  
도구 사용법은 [로컬-실행-가이드.md](로컬-실행-가이드.md)를 참고한다.

> 상태: **제안 초안** — 라벨을 다시 시작하기 전에 합의·수정한다.  
> 분할: chronological **train 60% / valid 20% / test 20%** (기본값).  
> **보안:** masked metric/PLMN ID와 원본명의 대응은 git·이 문서에 적지 않는다 (로컬 mapping 파일만).

---

## 1. 목표

라벨은 모델 출력이 아니라, **운영·연구상 “비정상으로 볼 만한 구간”의 합의된 정답**이다.

- 학습(OmniAnomaly 등)은 비지도로 이뤄지며, **train의 사람 라벨 구간은 학습에서 제외**된다.
- **valid** 라벨은 임계값·탐지 지표·UI 비교용이다.
- **test** 라벨은 최종 보고용이며, 튜닝을 보며 맞추지 않는다.

---

## 2. 이상의 정의 (무엇을 라벨하는가)

### 2.1 이상으로 본다 (`anomaly`)

다음 중 **하나 이상**이 뚜렷하고, 단순 시간대/요일 패턴으로 설명하기 어려울 때:

1. **성공·수락률 급락·낮은 지속** — SUCCESS / ACCEPT rate가 급격히 떨어지거나 낮게 유지됨  
2. **시도량 이상** — M971의 비정상적 급증·급락이 rate 이상과 동반되거나, 그 자체로 서비스 이상을 시사함  
3. **실패·타임아웃 계열 폭증** — FAIL / TO 등 관련 카운터가 크게 치솟음 (해당 metric을 기록)

경계는 **이상 구간만** 잡고, 전후 정상 변동은 넣지 않는다.  
애매하면 억지로 `anomaly`로 넣지 말고 `uncertain`을 쓴다.

### 2.2 성공률·수락률만으로 정답을 만들지 않는다

rate는 **후보를 찾는 렌즈**이지, 라벨의 **유일한 정의**가 아니다.

- 정답을 SUCCESS rate(또는 ACCEPT rate) 임계값·급락만으로 자동 확정하면, GT가 사실상 **1차원 신호**가 된다.
- 그러면 수십 feature 모델을 평가해도 “성공률 급락을 잘 맞추나?”에 가깝게 기울어, multivariate 탐지의 이점을 보이기 어렵다.
- 확정 절차:
  1. rate(+ M971)로 **스크리닝**
  2. FAIL/TO 등 **동반 신호**를 확인한 뒤에만 `anomaly`
  3. valid/test에는 rate 급락형만이 아니라, rate는 애매한데 **실패 계열만 튀는** 구간도 일부 포함
- 논문/보고에도 라벨이 “운영상 품질 이상(rate로 찾고 동반 지표로 확인)”임을 명시한다.

### 2.3 이상으로 보지 않는다 (라벨하지 않음)

- 매일/매주 반복되는 **주기적 피크·디프**(알려진 트래픽 리듬)
- **성공률·수락률이 일시적으로만 비정상적으로 올라갔다가 회복**하는 구간  
  — “좋은 쪽 이탈”이며, 통계적 패턴 이탈만으로 `anomaly`로 두지 않는다.  
  — 예외 검토: M971이 비정상적으로 꺼지며 rate만 치솟는 착시, 또는 직후 급락·실패 폭증과 **한 사건으로 이어질 때** → 그때는 동반 신호 기준으로 판단 (`uncertain` 가능)
- 짧은 스파이크 1~2포인트만 있고, rate·실패 지표에 **동반 신호가 없음**
- 매핑·결측·스케일만 이상해 보이는 **데이터 아티팩트**(가능하면 전처리로 처리)
- “모델이 이상이라고 했기 때문에”만으로 정답 승격 — **사람 확인 후에만** `anomaly`
- “통계적으로 평균에서 벗어난다”만으로 전부 `anomaly` — **운영상 의미**가 없으면 제외

### 2.4 불확실 (`uncertain`)

이상은 의심되지만 원인·범위가 불명확할 때.  
평가 지표에서는 **제외하거나 별도 보고**하는 것을 기본으로 한다 (합의 후 확정).

### 2.5 정상 (`normal`)

기본적으로 **라벨하지 않은 구간 = 정상 후보**로 본다.  
`normal` 라벨은 “여기만은 확실히 정상”을 기록할 때만 드물게 사용한다 (남용 금지).

## 3. 라벨 형식

| 항목 | 원칙 |
|------|------|
| 단위 | **구간(range) 우선**. 점(point)은 순간 이벤트만 |
| 시간 | 앱에 표시되는 **KST 벽시계** 기준으로 경계를 잡음 |
| 최소 길이 | 원칙적으로 **15분 이상**(5분 샘플 3개). 그보다 짧으면 point 또는 uncertain |
| 병합 | 같은 원인으로 보이는 인접 이상은 **하나의 구간**으로 합침 (사이 정상 간격이 30분 미만이면 병합 검토) |
| 기록 | `data/ib_data/labels/{PLMN}_labels.json` — kind / start / end / reasons / …

### 3.1 판정 기준 (`reasons`) — 저장 시 필수에 가깝게

라벨마다 **1개 이상** 선택(복수 가능). 라벨링 UI「판정 기준」체크리스트에 대응한다.

| 코드 | 의미 |
|------|------|
| `rate_degrade` | SUCCESS/ACCEPT rate **급락 및/또는 낮은 지속** |
| `attempt_drop` | M971 **급락** (rate와 같이 찍히는 경우 많음 → 복수 선택) |
| `attempt_spike` | M971 **급증** |
| `fail_surge` | FAIL/TO 등 **실패·타임아웃 폭증** → `fail_metrics`에 **해당 지표(복수)** 기록 |
| `other` | 기타 (메모 `note` 권장) |

- 전형적인 “rate 무너짐 + 시도량 감소” → `rate_degrade` + `attempt_drop`
- rate만 깨지고 M971은 유지 → `rate_degrade` (+ 가능하면 `fail_surge`)
- `fail_surge`면 UI에서 폭증한 metric을 고른다 (`fail_metrics`: `["M520", "M965", …]`)
- 성공률 **일시 급등**은 라벨하지 않으므로 reason 코드도 두지 않음
- ~~`multi_collapse`(시도량 유지·다지표 동시 붕괴)~~ — 사용하지 않음 (rate/fail/attempt로 충분)

JSON 예:

```json
{
  "id": "a1b2c3d4",
  "kind": "range",
  "start": "2026-07-01T03:00:00+00:00",
  "end": "2026-07-01T05:00:00+00:00",
  "reasons": ["rate_degrade", "fail_surge"],
  "fail_metrics": ["M520", "M965"],
  "note": ""
}
```

## 4. 분할별 라벨 전략

UI의 TRAIN / VALID / TEST 밴드를 기준으로 한다.

| 구간 | 역할 | 라벨 원칙 |
|------|------|-----------|
| **Train (앞 60%)** | 정상 패턴 학습 | 확실한 이상만 최소로. 많이지정해도 학습에서는 제외됨. “정상만 가득”이 이상적 |
| **Valid (가운데 20%)** | 탐지 평가·임계값·UI | **평가용 이상을 의도적으로 확보**. 너무 없으면 정의/대상을 재검토 |
| **Test (끝 20%)** | 최종 held-out | 라벨은 가능. 단, **모델을 본 뒤 맞춰 고치지 않음**. 잠근 뒤 최종 1회 평가 |

권장 순서:

1. Train·Valid를 먼저 훑고 라벨  
2. Test는 **모델 튜닝을 끝낸 뒤**에만 열거나, 열더라도 수정 로그를 남김  
3. 1차 학습 후 Valid에서 FP/FN만 재검토 (정의 변경이 필요하면 문서부터 수정)

---

## 5. 화면에서 보는 순서 (권장)

1. **SUCCESS rate / ACCEPT rate** + **M971**으로 후보 구간 스크리닝  
2. 후보마다 **FAIL/TO·관련 카운터**로 동반 신호 확인 (rate만으로 확정하지 않음)  
3. 구간 시작·끝을 rate·M971이 정상으로 돌아오는 지점에 맞춤  
4. **판정 기준**을 체크하고, `fail_surge`면 해당 metric 선택  
5. Valid에 **유형이 치우치지 않았는지**(rate급락만 잔뜩 있지 않은지) 확인 후 저장

---

## 6. 품질·일관성

- 이 문서를 **라벨 가이드**로 세션 시작 전에 한 번 읽는다.  
- 애매한 케이스는 예시로 문서 하단에 2~3개 추가한다 (포함 / 제외).  
- 가능하면 **이틀 뒤 재검** 또는 2인 교차.  
- 모델 오버레이는 **힌트**일 뿐, 사람 라벨을 자동 대체하지 않는다.  
- 라벨 정의가 바뀌면 **버전/날짜**를 이 문서에 남기고, 필요 시 해당 PLMN을 재라벨한다.

## 7. 초안에서 미합의 (다음에 정할 것)

- [ ] uncertain을 F1 계산에서 제외할지 / 별도 리콜로 보고할지  
- [ ] 최소 구간 길이를 15분으로 할지, 10분으로 할지  
- [ ] 1차 대상 PLMN (예: P0480만 vs top-N)  
- [ ] Valid에 목표로 둘 이상 구간 개수 (예: 5개 이상)
